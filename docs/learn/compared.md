*Design phase: the program has only the command `version`, so everything below that you could run today is somebody else's tool. Facts about other projects were read on 2026-11-02 at the link beside each; the quotations are in [the sources page](/research/private-root-alternatives-2026-11-02/). Projects change: check the link before you decide.*

**Today, use one of these. Read ritueel to know why you are doing each step.** The tools below are shipped and in use. ritueel is a design and a set of teaching pages, and it asks you to wait for a tool that does less copying and more recording. This page says when waiting is not worth it.

It sits at the end of [Learn](/learn/): the question "which root custody should I choose?" has an answer here that depends on [where a key lives](/learn/key-stores/) and [what a key store can prove](/learn/what-a-store-can-prove/).

## The options at a glance

Under each option below, "what ritueel adds" is designed or taught, not built, unless the text says it is built.

| Option | A root made where | Copies of the root key |
|---|---|---|
| [offline-pki](#offline-pki) | On the computer, then imported into each root YubiKey. | One per root YubiKey. |
| [Smallstep's YubiKey recipe](#smallsteps-yubikey-recipe) | On disk, imported into each root YubiKey, file shredded. | One per root YubiKey. |
| [The drduh guide](#the-drduh-yubikey-guide) | On an offline computer, backed up to encrypted storage. | The backups, kept offline. |
| [OpenBao](#openbao) | In OpenBao's storage, unless you keep the root elsewhere. | The key can be exported only at generation time. |
| [YubiHSM 2](#yubihsm-2) | On the device, which can attest it. | Only by wrapped export, if you allow it. |
| [Sequoia `sq`](#sequoia-sq) | OpenPGP keys only, no X.509. | Not covered by the pages read. |
| [AWS KMS alone](#aws-kms-alone) | In the service. | None you can take; a replica the service keeps. |

## What ritueel adds, and what it does not

ritueel adds three things. None of the options above, as read on 2026-11-02, does all three.

1. **Teaching with measurements.** Which verifier honours a revocation ([What a revocation reaches](/learn/revoke/#what-a-revocation-reaches)), how Go and OpenSSL differ on name constraints ([Private PKI](/learn/chain-private-pki/)), why two certificates for one intermediate can break a path builder ([Two roots](/learn/two-roots/)), and what a custody chain is as distinct from a signature chain ([Custody chain](/learn/custody-chain/)). This is built: the pages exist.
2. **Root keys born in their key store, with attestation, a history and a trust sequence.** A root key is made inside its card or cloud key and never leaves, a token's attestation proves it ([What a key store can prove](/learn/what-a-store-can-prove/)), every ceremony is written to a hash-chained record ([The history](/learn/the-history/)), and a signed root list carries a sequence number that a host can check ([record 0006](../decisions/0006-bundle-history-and-trust-files.md)). This is designed, not built.
3. **A written hand-off with test vectors** between a root custodian and a system that holds intermediates ([the contract](/reference/hand-off-contract/#test-vectors)). The contract and its vectors exist; no tool implements either end yet.

ritueel does not offer **M-of-N control**: any one active key signs alone, and [the accepted limit](../decisions/0002-where-a-key-lives.md) says so. It does not offer **Ed25519 roots**: P-384 is the one algorithm that every key store holds and that was tested with every verifier the project ran ([record 0009](../decisions/0009-release-keys-and-the-keyring.md), Roads not taken). And it is **not the daily tool**: you will keep using `gpg` and `step` for daily work, and ritueel is the occasional ceremony, a single command-line program that is planned ([the roadmap](/roadmap/)).

## offline-pki

**What it does.** A small Python application for an offline PKI, with a root and an intermediate on YubiKeys and an air-gapped board that resets at each boot ([post of 2025-03-17](https://vincent.bernat.ch/en/blog/2025-offline-pki-yubikeys), read 2026-11-02). It uses three YubiKeys: "2 YubiKeys for the root CA (with a 20-year validity), 1 YubiKey for the intermediate CA (with a 5-year validity)". The root key is made on the computer and imported: "The key for the root CA is not generated by the YubiKey. Using an air-gapped computer is all the more important." Its [README](https://github.com/vincentbernat/offline-pki/blob/main/README.md) (read 2026-11-02) lists "no CRL support" and a hard-coded P-384 curve, and warns that the tool does not display certificate content, so you check the request yourself.

**Better when** you want almost exactly this niche today, from a small project, and a copied root on two cards is acceptable to you.

**What ritueel adds:** an attestation for a key made on the card, a revocation list, a history, and the teaching. **What it lacks:** a tool that runs. The key is not copied in ritueel, so a lost card is a loss to survive with the second key, as [Two roots](/learn/two-roots/) explains.

## Smallstep's YubiKey recipe

**What it does.** A recipe by a Smallstep member ([discussion 1591](https://github.com/smallstep/certificates/discussions/1591), 2023-10-20, read 2026-11-02): "A YubiKey can be a good place to store a Root CA, because the key will not be exportable, but you can use it to sign new intermediate CAs as needed." It starts "First, generate your root key pair on disk", imports the key into each root YubiKey, and shreds the file. The intermediate lives on another YubiKey for step-ca's online signing. The author adds that requiring several people "is very challenging to operationalize and is beyond the scope of this tutorial".

**Better when** you want one toolset for the root ceremony and the online CA, and you accept a root that existed as a file once.

**What ritueel adds:** a key that was never a file, and a record. **What it lacks:** the online CA. ritueel never holds an intermediate; a system like [sluis](https://sluis.id) does ([record 0001](../decisions/0001-what-ritueel-is.md)).

## The drduh YubiKey guide

**What it does.** The standard guide for an OpenPGP key on a YubiKey, with 13,062 stars and a commit on 2026-11-02 ([repository](https://github.com/drduh/YubiKey-Guide), read 2026-11-02). "Keys are first generated on an offline computer, then exported to encrypted offline backups, and then transferred to YubiKey for daily use." The primary, which the guide calls the Certify key, "is the offline primary key and should not have an expiration date"; subkeys expire in two years. A revocation certificate is mentioned in one footnote, and no step makes one.

**Better when** you want a person's OpenPGP identity today. It is widely followed, and it teaches the commands.

**What ritueel adds:** revocation signatures made at birth and stored apart, a drill that proves the restore, and a history. The primary of a person stays offline in a file in both ([record 0008](../decisions/0008-a-persons-own-key.md)), so the difference is in the record and the drills, not in where the key lives. **What it lacks:** the years of use.

## OpenBao

**What it does.** A secrets manager whose PKI engine signs intermediates. Its own page says "OpenBao storage is secure, but not as secure as a piece of paper in a bank vault. It is, after all, networked software. If your root CA is hosted outside of OpenBao, don't put it in OpenBao as well; instead, issue a shorter-lived intermediate CA certificate and put this into OpenBao" ([PKI considerations](https://openbao.org/docs/secrets/pki/considerations/), read 2026-11-02). A root mount used only to sign intermediates is its "common pattern". Latest release v2.7.2, 2026-10-26.

**Better when** you already run it and accept a software root in a sealed mount, or you keep the root elsewhere and use OpenBao for the online part.

**What ritueel adds:** the root outside the server, which is what the page above advises, with the ceremony taught. **What it lacks:** everything online. ritueel is not a secrets manager.

## YubiHSM 2

**What it does.** A hardware security module the size of a USB stick. It makes keys on the device and "attestation is also supported for asymmetric key pairs generated on-device"; its log is hash-chained ([product page](https://www.yubico.com/product/yubihsm-2/), read 2026-11-02, v2.4, EUR 786.50 including VAT). It supports "M of N rules on the wrap key used to export keys for backup or transport", so several administrators are needed to import a backup. The [user guide](https://docs.yubico.com/hardware/yubihsm-2/hsm-2-user-guide/hsm2-backup-restore.html) says the split "is done in the software" and "the YubiHSM2 itself is not aware of such split or any shares", so it protects the backup and does not require several people to sign.

**Better when** you need a hardware module, an on-device audit log or the backup split, and the price is acceptable.

**What ritueel adds:** a root on a card, whose price is on [Which keys to buy](/learn/which-keys-to-buy/), with a card's attestation, and the teaching. **What it lacks:** a hardware module, an on-device log and the backup split. ritueel's [two cards are redundancy, not control](../decisions/0003-root-cards.md).

## Sequoia `sq`

**What it does.** A command-line tool for OpenPGP. Version 1.0 on 2024-12-16 was its first stable release, with "we will no longer change sq's CLI in an incompatible manner" ([Sequoia blog](https://sequoia-pgp.org/blog/2024/12/16/202412-sq-1.0/), read 2026-11-02); 1.5.0 was published on 2026-10-07 ([docs.rs](https://docs.rs/crate/sequoia-sq/latest)). It rejects a revoked key, while `gpgv` ignores the revocation ([What a revocation reaches](/learn/revoke/#what-a-revocation-reaches), measured 2026-11-01).

**Better when** you want modern OpenPGP tooling, or a verifier that honours revocations.

**What ritueel adds:** the root ceremonies around an OpenPGP primary key, and X.509 as well. ritueel plans to build OpenPGP packets itself, with a patched library, rather than call `sq` ([record 0010](../decisions/0010-the-engine-the-process-and-the-page.md)). **What it lacks:** the tool.

## AWS KMS alone

**What it does.** Keys that "are protected by FIPS 140-3 Security Level 3 validated hardware security modules (HSM). They never leave AWS KMS unencrypted" ([overview](https://docs.aws.amazon.com/kms/latest/developerguide/overview.html), read 2026-11-02). A multi-Region key is the same key in several Regions: "Each set of related multi-Region keys has the same key material and key ID" ([multi-Region keys](https://docs.aws.amazon.com/kms/latest/developerguide/multi-region-keys-overview.html), read 2026-11-02).

**Better when** you are an AWS organisation that wants an audited, policy-gated root without cards, and you are happy to write the policy and the signing steps yourself.

**What ritueel adds:** the policy it reads back every time, the confirmation of what is signed, and the record. **What it lacks:** the account and the tooling around it, which [the cloud-root guide](/guides/prepare-the-cloud-root/) says are yours to set up.

## Which one, today

| You are | Use today | Then read |
|---|---|---|
| A person with an OpenPGP identity | The drduh guide, with `sq` to verify. | [Personal OpenPGP](/guides/personal-openpgp/) and [Revoke](/learn/revoke/). |
| A small team that wants a root and an intermediate on YubiKeys | offline-pki, or Smallstep's recipe if you run step-ca. | [Where a key lives](/learn/key-stores/#which-path-is-yours), for what the copy costs you. |
| An organisation on AWS | AWS KMS with your own policy and runbook. | [The cloud root](/guides/prepare-the-cloud-root/). |
| An organisation that needs several people to sign | YubiHSM 2 or an HSM with your own procedure. | [Layered trust](/learn/layered-trust/). |

ritueel becomes the better choice when its first milestones exist and the cloud path is built. Until then, use one of these, and read ritueel to know why you are doing each step.
