*Design phase: these are the principles the design follows today. Each links to the record or page that decides it. Principles 1 to 10 carry the same numbers as in [sluis](https://sluis.id), a system that holds intermediates. Principles 11 and up are each product's own, numbered from one common sequence, so a number never means two things.*

## What ritueel is, and is not

- **Teaching first, then tools that simplify the rituals.** The mission is that ritueel helps one person or a small team keep a private root and an OpenPGP primary key for years without losing it, leaking it, misusing it or letting it expire. It teaches the model first, and its tools run each ceremony with the person deciding. See [record 0001](decisions/0001-what-ritueel-is.md).
- **A command-line tool with a guided mode and a read-only local page, and documentation, not a network service.** It signs nothing online. See [record 0001](decisions/0001-what-ritueel-is.md).
- **It owns roots, root ceremonies and root transitions** for X.509, OpenPGP and SSH CA roots, personal OpenPGP keys included. See [record 0001](decisions/0001-what-ritueel-is.md) and [record 0006](decisions/0006-bundle-history-and-trust-files.md).
- **It never holds an intermediate's private key.** Systems like [sluis](https://sluis.id) hold intermediates, and meet ritueel only through the [hand-off contract](/reference/hand-off-contract/).
- **Its records are files the holder keeps:** ceremony records, root lists, and the keyring file that ritueel makes and the user's own pipeline packages and publishes. See [record 0006](decisions/0006-bundle-history-and-trust-files.md) and [record 0009](decisions/0009-release-keys-and-the-keyring.md).
- **One maintainer, almost no program code yet, no independent review yet.** ritueel is maintained by one person with AI agents and has had no independent security review. The program has one command, `version`; the local page exists as code and as a demo (`ui/`, `proto/`). ritueel is a design, a teaching site and a demo. [GOVERNANCE.md](https://github.com/truvity/ritueel/blob/main/GOVERNANCE.md) says how that changes.

## The principles

Each principle is marked **Shared** with sluis or **ritueel's own**. The shared principles come first, 1 to 10.

1. **Every key is born in its key store and never leaves it.** *Shared.* A transition makes a new key, and the old one vouches for it. For a software key held in a replicating key store (1Password), [the key store's own replication](/learn/key-stores/) is its backup; an encrypted file copied elsewhere is a second copy of the key and is handled as [record 0002](decisions/0002-where-a-key-lives.md), rule 11, says. ritueel never exports a key from a card or a KMS. Wrapped data keys in a backup are escrow of data, not of keys. See [record 0002](decisions/0002-where-a-key-lives.md) and [Root and intermediate](/learn/root-and-intermediate/) and [Moving from one root to another](/learn/transitions/). *For a person's own key in ritueel there are two stated exceptions, an adopted primary and an encryption subkey made in software: [record 0002](decisions/0002-where-a-key-lives.md), rule 2.*
2. **Trust is layered, and redundancy answers loss, not compromise.** *Shared.* There are two root cards because a card cannot be copied, and one KMS key plus a replica because KMS can replicate its key. A compromise is answered by revocation and a transition. A revocation skips every overlap period that exists for healthy rotation. See [record 0002](decisions/0002-where-a-key-lives.md) and [Two roots in practice](/learn/two-roots/).
3. **Keys are shared and rotated by rule.** *Shared.* A key is shared only where audience, lifetime, revocation coupling and callers are all equal, as for the X.509 root key that also signs the root list. Renewal re-signs. Key material is replaced on an event: an advisory that affects the device, its firmware or the service, the deprecation of its algorithm, loss or end of life, a suspected compromise, or a change of key store or custody; the holder reviews the advisories at every yearly ceremony. A key that can be copied, a software key, is also replaced at most every three years. A transition makes a new key, never a copy. See [the slot map](decisions/0003-root-cards.md) and [renewal and replacement](decisions/0007-changing-and-losing-a-root.md).
4. **Verify; never trust a claim.** *Shared.* Attest what can be attested, re-read KMS keys and their policies from the service, and accept no copy of either. A check that cannot run is reported as not run, never as passed. See [What the tool checks](/tools/cli/#what-the-tool-checks) and [the proof file](/reference/hand-off-contract/#the-proof-file).
5. **Open standards, as their consumers implement them.** *Shared.* OpenPGP keys are version 4 while `gpg` has no version 6, and a revoked key leaves the keyring package because `gpgv` ignores revocations. See [record 0009](decisions/0009-release-keys-and-the-keyring.md).
6. **A written contract and test vectors, not shared code; things are named for what they are.** *Shared.* The word is `intermediate`, not the name of a device. See the [hand-off contract](/reference/hand-off-contract/) and its [test vectors](/reference/hand-off-contract/#test-vectors).
7. **A person only where a person adds safety.** *Shared.* A touch on a card and a typed digest of the plan need a person; routine work reads public files only and is automated. A renewal over the same key is routine, and `apply` finds it from the end date; a person still confirms its plan and is required to make a root key, to change the root keys, and to certify a new key. See [record 0005](decisions/0005-a-ceremony-and-where-it-runs.md) and [What a ceremony is](/learn/ceremonies/).
8. **Nothing without a consumer.** *Shared.* A key store, a command or an option arrives with its first real installation or caller. See the [roadmap](/roadmap/) and [how decisions are made](/contributing/decisions/).
9. **Measure, and date the measurement.** *Shared.* A claim about a tool, a card or a service carries the day it was measured. See [the research pages](/research/).
10. **Public by default, private where it protects.** *Shared.* The design, the reasons and the roads not taken are public; secrets and private deployment details are not. See [Public content and secrets](/contributing/public-content/).

11 and 12 are sluis's own; 13 to 15 are ritueel's; a new principle takes the next free number, whichever product adds it.

13. **Two keys are redundancy, not control.** *ritueel's own.* Any one active root key signs alone, and ritueel never claims otherwise: a second card is not a spare, two cards are not two-person control, and a replica is not a second key. The exception is ritueel's own root list: changing the root keys requires every current root key, or its stored removal authorisation ([the root list](/reference/root-list/#who-signs)). See [the accepted limit](decisions/0002-where-a-key-lives.md) and [Two roots in practice](/learn/two-roots/#the-limit-you-accept).
14. **ritueel teaches first.** *ritueel's own.* Every ceremony is explained, every road not taken is recorded, and a guide walks through each transition. The tools exist to simplify the rituals, and the guided mode and the local page are faces of the same ceremony engine, not second implementations. See [record 0001](decisions/0001-what-ritueel-is.md) and [A lost root card](/guides/lost-root-card/).
15. **Succession is the holder's duty.** *ritueel's own.* A root that others rely on outlives its holder's attention only if a named second person can find the cards, the PINs, the bundle and the revocation material, and has run the restore check. That is an organisational duty, like renewing a domain; ritueel reminds, as a registrar does, and does not take it over. The reminder is `ritueel status`, which warns before anything expires and when the newest restore report is old. See [record 0002](decisions/0002-where-a-key-lives.md), [the restore check](/reference/drill/#the-restore-check) and [when a drill is due](/reference/drill/#when-it-is-due).
