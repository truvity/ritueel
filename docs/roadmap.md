The plan is public and small. Each milestone delivers something a person can use, and each work item is an [issue](https://github.com/truvity/ritueel/issues) with a "done when". Dates are not promised; the order is.

**Status as of 2026-11-11:** design phase. M0, the written design, is this round of records and pages. The [decision records](/decisions/) are accepted, and every format that M2 to M6 build is specified on the [reference pages](/reference/). The hand-off contract (with the SSH CA key request), the root list, the SSH CA key list and the CRLs have test vectors; the keyring package is a specification that its builder will check. The program has no code yet. The local page exists as code and as a demo (`ui/`, `proto/`). What is open lives in the issues and their milestones, not on this page. The GitHub milestones carry the older names until a maintainer script renames them.

**Design: 18 decision records, 18 reference pages. Code: 0 lines.** Counted on 2026-11-11, in Go only; the page in `ui/` is TypeScript and is counted apart. The home page counts them at each build, and the [project status](/status/) page adds the issues closed in each milestone.

## The first version

Three stores behind one ceremony: a software key in an encrypted file, a pair of root cards, and one cloud key service with a replica. The cards are built after the first signed release, so the first release does not wait for them.

### The gate before the first signed release

The first signed release (M5) follows the adoption of the project's root and its drill (M4): the root adopted, attested or read, its revocation signatures stored apart, and the adoption drill passed ([issue #48](https://github.com/truvity/ritueel/issues/48), the end of M4). Card roots are added after it (M6), as a transition that [the keyring package](/decisions/0006-release-keys-and-the-keyring-package/#the-keyring-package) already carries. The release-key tests come first, so the first signed release can follow the gate at once. A software root serves tests, drills and development, and never anchors a signed release ([ADR 0006](/decisions/0006-release-keys-and-the-keyring-package/#no-signed-release-before-the-gate)).

### Order and reasons

- M1 comes first because the default way to open a key file rests on a passkey that has not been tried, and the card rows rest on a deletion that has not been tried. If a proof fails, the fallback of its record applies and nothing else changes.
- M2 follows because everything later needs the engine, the ledger and the stores a release candidate carries. The `aws-kms` store that adopts a key is in it, because the cloud root is the recommended path for a team with a cloud account ([which path is yours](/learn/key-stores/#which-path-is-yours)) and it has no card to alternate. The first consumer needs a build it can pin; a tagged, unsigned candidate gives it one.
- M3 needs the key files and the engine of M2. It comes before the roots of a company because a person's key is the smaller case.
- M4 needs M2: the drill walks through the cloud store and the records, and through `root revoke` and `root add`, so the transitions are built in M4 with it. M4 ends with the gate, so nothing later depends on a root that was never drilled.
- M5 follows M4 because the release subkey is bound by the project's root, and because the root's key is published in the keyring package, built in M5.
- M6 follows M5 because card roots need the card proofs of M1, the inventory of M2 and the transitions of M4 (a card root joins the set by `root add`), and the first release does not need them.
- M7 is last: each item arrives with its first real installation or caller (principle 8).

## After the first version

None of these is planned in detail. Each starts as a decision proposal; the staff delegation and the renewal of a cloud root are also listed in M7.

- **Staff OpenPGP** ([ADR 0014](/decisions/0014-staff-openpgp-primaries-sealed-in-sluis-subkeys-born-on-cards-ritueel-makes-the-card-ready-and-runs-the-delegation/), [the reference](/reference/staff-openpgp/), [issue #103](https://github.com/truvity/ritueel/issues/103)): a staff key is a primary that sluis seals for each person and company, with subkeys born on the person's card. ritueel's part is the delegation ceremony and a card helper that writes the proof bundle `sluis key bind` reads. It is designed and decided, and built after the first signed release because it needs the `openpgp-card` store (M3) and real roots (M4). Its order:
  1. The conformance test on a real rehearsal card: the attestation of the card-born subkeys, the card's back-signature over a software primary, and the certificate accepted by `gpg`, `gpgv`, `sqv` and the hosting platform.
  2. The card helper and the proof bundle, with their vectors.
  3. The delegation ceremony: the root's trust signature over each company's certification key, and an ordinary certification over its keyring-signing key, once the real roots exist. The primary, the binding, the certification, the keyring and the sync are sluis's work, not ritueel's.
- Renewal of a cloud root without a person ([the cloud root](/reference/kms-root/#renewal-under-a-policy)): designed, built after the first release candidate.
- Files for a key on one's own domain (WKD) and the DNS record text, as a later output of ritueel with a guide.
- More key stores, each arriving with its first real installation and passing [the admission test](/decisions/0003-key-stores-and-the-card-layer/#planned-stores): Google Cloud KMS, Azure Key Vault ([issue #67](https://github.com/truvity/ritueel/issues/67)) and Nitrokey ([issue #66](https://github.com/truvity/ritueel/issues/66)) are planned, then other clouds, HSMs, TPMs and other cards. The site compares them and says which to buy for testing.
- A post-quantum root ([issue #32](https://github.com/truvity/ritueel/issues/32)).

### What is delivered

- One statically linked executable for Linux.
- A small release signer program for CI, used by the release workflow until the requester system signs natively ([ADR 0006](/decisions/0006-release-keys-and-the-keyring-package/#ritueels-own-releases)).
- Later, a Go library for infrastructure code. It creates the cloud keys and their policies from the same policy package that the program uses to check a key.

## How to follow

The milestones are GitHub milestones on the repository, and the [project status](/status/) page shows how many issues each has closed. The issues carry the labels `area:*` and `type:*`. A change to this plan is a pull request to this page.
