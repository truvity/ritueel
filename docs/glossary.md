These words carry the design. The pages and the records use each in the sense below and in no other. Where a page keeps an older or narrower word, the third column says so: the glossary does not rename a page's word. It defines words from the records; it decides nothing new.

| Word | Meaning | The page word | Decided in |
|---|---|---|---|
| **root** | One thing that outsiders trust without further proof, of one kind: an X.509 trust anchor, an OpenPGP identity or an SSH CA. A root is built from one or more keys, each in one place (a card slot, a cloud key or a key file) and labelled A, B, then the next letter. Each key is born in its store. | `root`; `root key` for one key of it; `primary` for an OpenPGP root key | [0001](decisions/0001-what-ritueel-is.md) (rule 28), [0002](decisions/0002-where-a-key-lives.md), [What is a root?](/learn/what-is-a-root/) |
| **delegated key** | A key that a root certifies or binds: the key of an intermediate certificate, an OpenPGP subkey or the SSH CA key of a system. A **delegation** is a declared name under a root for a key that does daily work; the name stays when the key is replaced. | `intermediate` for the X.509 case; the hand-off contract keeps this word | [0001](decisions/0001-what-ritueel-is.md), [hand-off contract](/reference/hand-off-contract/) |
| **holder** | The person, or the small team, who keeps a root and runs its ceremonies. | `holder`, `operator` for the one who prepares a card or an account | [0001](decisions/0001-what-ritueel-is.md) |
| **requester** | The system that holds delegated keys and asks a root for a certificate or a binding through the hand-off contract. [sluis](https://sluis.id) is one. | `requester`, with ritueel the `certifier` | [hand-off contract](/reference/hand-off-contract/) |
| **store** | The kind of place where a key is born and kept: a software key file, a PIV card, an OpenPGP card or a cloud key service. A key's **place** is the one slot, cloud key or file where it lives; it never leaves it. | `store`, `key store` | [0002](decisions/0002-where-a-key-lives.md), [Where a key lives](/learn/key-stores/) |
| **ceremony** | One act that uses a root key, in six steps: plan, confirm, reserve, sign, verify, record. `apply` runs it and a person confirms it. After it ritueel prints what to do. | `ceremony`; the practice of meeting the root once a year is called the yearly ceremony (there is no yearly command) | [0005](decisions/0005-a-ceremony-and-where-it-runs.md), [0011](decisions/0011-publishing-and-what-to-do-after-a-ceremony.md), [What a ceremony is](/learn/ceremonies/) |
| **bundle** | The directory with a fixed structure that holds everything ritueel knows about one trust domain: its wanted files, history, trust sequence, root list, root keys and card files. A holder with a personal key and a company keeps two. A root key is written with the bundle's name across bundles, for example `acme/A`. | `bundle`, always; `directory` only for any other directory (key directory, working directory); the trust file is `the CA bundle` in full | [0006](decisions/0006-bundle-history-and-trust-files.md), [The bundle](/reference/bundle/) |
| **history** | The write-once part of the bundle: the folder `history/`, one ceremony folder for each ceremony, holding its plan, exact copies of the wanted files the plan used, attempt, birth journal, journal of signatures, transcript and ceremony record. The end of the history is the ceremony record that no other ceremony record names; two ends are a fork. | `ledger` is the older word; `history` for this part, `bundle` for the whole | [0006](decisions/0006-bundle-history-and-trust-files.md), [The history](/learn/the-history/) |
| **record** | The JSON file that ends a ceremony, written last in its ceremony folder. It names the ceremony record before it by digest, so the ceremony records form a hash chain, and it lists what the ceremony wrote by digest. | `ceremony record`, in full | [0006](decisions/0006-bundle-history-and-trust-files.md), [Ceremony files](/reference/ceremony-record/) |
| **renew** | Extend the validity of the same key: a new certification (a certificate or a binding) over the same key material. No key is made. A **certification** is what a ceremony makes when one key vouches for a subject from a day to a day; a delegation or the root list is due 60 days before its end date. | `renew`, `re-sign` | [0007](decisions/0007-changing-and-losing-a-root.md), [Re-signing](/learn/re-sign/) |
| **replace** | Make a new key on an event, and let the old one end: an advisory, an algorithm that is deprecated, a lost card, a suspected compromise, a change of store, or the three-year limit on a key that can be copied. | `replace`, `rotate` | [0002](decisions/0002-where-a-key-lives.md), [0007](decisions/0007-changing-and-losing-a-root.md), [Rotate](/learn/rotate/) |
| **trust files** | The files that outsiders read to decide whom to trust: the root list, the CA bundle, the CRLs, the SSH CA key list and the public OpenPGP keyring, one numbered trust set in the `trust/` folder of the bundle. A personal bundle has only the person's public certificate. ritueel builds them; the holder's pipeline publishes them, and ritueel prints what to do. | the older page word `trust products` goes | [0006](decisions/0006-bundle-history-and-trust-files.md), [0011](decisions/0011-publishing-and-what-to-do-after-a-ceremony.md) |
| **wanted** | What a person writes about how the bundle should be: `ritueel.yaml` for settings, and one file for each card, root, delegation and the user IDs, in strict YAML, only on the workstation. A ceremony never writes a wanted file. | `wanted file` | [0006](decisions/0006-bundle-history-and-trust-files.md) (rules 11 and 29), [0005](decisions/0005-a-ceremony-and-where-it-runs.md) |
| **not applied yet** | What is wanted and is not done, found every time from the wanted files, the history, the date and the requests. It is never stored. Each item is a change, shown on its object. A change is not a row: a row is a row of slots on a card. | `not applied yet`, `a change` | [0005](decisions/0005-a-ceremony-and-where-it-runs.md) (rule 29) |
| **apply** | Do the changes that are not applied yet in one ceremony. `ritueel apply` finds them and writes the plan; after the person confirms, it signs and records. `apply PLAN` runs a plan made before, elsewhere. | `apply` | [0005](decisions/0005-a-ceremony-and-where-it-runs.md) (rules 4 and 10) |

The words `card`, `row` and `card file` are defined on their own pages: [the bundle](/reference/bundle/) and [cards](/reference/cards/). Those pages still say `inventory` and are rewritten to follow the records.
