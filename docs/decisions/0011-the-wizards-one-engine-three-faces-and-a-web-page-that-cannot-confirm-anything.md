# 0011 — The wizards: one engine, three faces, and a web page that cannot confirm anything

**Status:** Accepted
**Date:** 2026-11-11

## Context

[0007](/decisions/0007-ritueel-teaches-and-its-tools-simplify-the-ceremonies/) decides that ritueel has three faces, the command line, a guided mode and a local page served on localhost, that all are the one ceremony engine of [0004](/decisions/0004-ceremonies-plan-confirm-reserve-sign-verify-record/), and that the page follows eight security rules. It does not say how a front end uses the engine, what the guided mode looks like, what the page may do about a confirmation, or what the rules mean in code. The page exists as code and a demo (`ui/`, `proto/`); the program that serves it is built in M2 ([issue #17](https://github.com/truvity/ritueel/issues/17)), and the guided mode comes after the first signed release ([issue #16](https://github.com/truvity/ritueel/issues/16)). The maintainer chose the same stack as sluis (ConnectRPC) and asked that the command line and the page work the same way over one process, started on demand and reached by the command line through a Unix socket (2026-11-11). A browser cannot open a Unix socket, so the page needs a second door. In this record, a wizard is the guided mode or the page. The threats are in [a dated research page](/research/local-wizard-threats-2026-11-01/). The mission test applies hardest here: a friendly front end is the place a tool starts deciding for the person.

## Decision

- **A wizard is a front end over the plan.** It builds the options of a command, asks the engine for the plan, shows it with its digest, and hands the confirmation to the terminal. It has no code that builds a request, a plan or a signature, and every step prints the equivalent command line. A test runs a wizard session, runs the printed commands, and compares the plans and the records ([the profile](/reference/wizard/#one-engine)).
- **The command line and the page call one API of one ritueel process.** It is written in Protobuf and served with ConnectRPC (package `ritueel.local.v1alpha1`, in `proto/`; the page is in `ui/`). The process is the same program as the command line, started on demand by the first command that needs it. It has two doors. The command line reaches it through a Unix socket that only the same user can open, and may call every method, including the ones that confirm, sign and run a ceremony; the digest a person types in the terminal travels over this socket. A browser cannot open a Unix socket, so for the page the same process also listens on the IPv4 loopback address, only while the page is in use, with the token rule of [the profile](/reference/wizard/#the-web-page-the-security-profile). That listener serves only the page's part of the API, the reads and `SavePlan`: no call that confirms, signs, creates a key or runs a ceremony is registered on it. A ceremony is still confirmed in the terminal.
- **The guided mode asks line by line,** in plain text, with no full-screen interface and no dependence on colour. A screen reader, a log and a pipe all work, and without a terminal it refuses rather than prompt.
- **The web page cannot confirm anything.** It has no control that confirms a plan, signs, creates or deletes. It shows the plan and its digest, says "type the first eight characters in the terminal", and follows the state of the ceremony; the terminal prompt of [0004](/decisions/0004-ceremonies-plan-confirm-reserve-sign-verify-record/#six-steps-every-ceremony) waits for the person. The page is a read-only view: it never confirms a ceremony and never sees a secret. Read-only means that the page changes no key, no ceremony and no record; the one thing it writes is a plan file, and the process writes it. Its wizard ends with a preview and the command to run (`ritueel run PLAN --confirm DIGEST`). The page calls `SavePlan`, and the process writes the plan exactly where `--plan-only` writes it, `ledger/<ceremony>/plan.json` of the directory ([the ceremony record](/reference/ceremony-record/)), so that the holder can boot the offline system and run it there ([0016](/decisions/0016-several-roots-share-one-pair-of-root-cards-and-the-directory-keeps-a-card-inventory/#where-a-plan-runs)). The page's listener has no call that confirms, signs, creates a key or runs a ceremony, because those methods are not registered on it at all; `SavePlan` rebuilds the plan and refuses a digest that differs from the rebuilt plan's. This is [0007](/decisions/0007-ritueel-teaches-and-its-tools-simplify-the-ceremonies/#the-wizards-security-rules) rule 7 made structural: a page that never held the control cannot be tricked into using it, whoever else is on the machine.
- **The eight rules of 0007 are a profile with a test for each row,** on [one reference page](/reference/wizard/#the-web-page-the-security-profile): the IPv4 loopback literal on a random port, a one-time token that becomes an `HttpOnly`, `SameSite=Strict` cookie, an exact `Host` check and a separate cross-origin check, embedded assets, a strict policy, no telemetry, and a session that ends. The program prints the address and does not start a browser: that would put the token on a command line other processes can read.
- **The page is a single-page application** in React and TypeScript with MUI and Tailwind CSS, built with Vite from a lock file (`ui/package-lock.json`, versions pinned exactly), built in CI and embedded in the program as static files. Its contract is Protobuf, called over ConnectRPC. Nothing is remote, there is no inline script, and scripts come only from `'self'`. The component library (Emotion, under MUI) writes styles at run time, so `style-src` allows `'unsafe-inline'` while `script-src` never does. The CSP stays free of hashes.
- **What protects the page today** is what exists in the code of the page: exact versions and a lock file; a generated client that is committed and diffed by `just proto-check`; a `ui` job in the checks; a scan of the source for `innerHTML`, `eval`, `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket` and remote URLs; a test that hostile strings (a bidirectional override, a joiner, control characters) reach the markup only as visible `U+XXXX` escapes; a check of the built files that finds no remote host and no fixture in the real build; a headless-browser run under the site's exact headers with no console or policy violation; and no call with a field for a secret, a PIN or a passphrase. The profile's tests of the program are still to write.
- **The wizards drive the ceremonies and the checks, not the preparation.** `init`, `due` and `run`, the intermediate and root commands, the builders and verifiers, the drills and the personal commands are in; preparing a card, changing a PIN and publishing are the holder's, and the wizard names the guide for them.
- **The explanation of each step is written once,** in one catalogue read by both faces, and names the Learn page that holds the reason. The wizard teaches where it acts.
- **The page is usable by keyboard and by screen reader.** A single-page application needs script, so a plan is read in the terminal (`--plan-only`, the guided mode) or in the saved plan file instead.
- **The process is not a service.** It is not installed as a system service, is never started at login or boot, and never survives a reboot. It ends by itself after an idle time and on `ritueel stop`. Between calls it holds nothing secret: a PIN, a passphrase, the contents of a key file or a cloud session exists in it only during the call that needs it and is cleared when the call ends, and a card is opened for a ceremony and closed after it. It keeps no ceremony state either: every call reads the directory again, so a killed process loses nothing. Where the socket lives, the idle time and what happens when a process of another version answers are in [the reference](/reference/wizard/#the-ritueel-process) and are proposed there.

## Consequences

- A person who wants a mouse still touches the terminal for every irreversible step, and runs the printed command, or the saved plan, there. That is the price of rule 7, and the same price as the card's touch.
- A tree of npm packages (React, MUI, Emotion, Vite, Tailwind, ConnectRPC) sits in the build of a program that works on root keys, and nobody has audited it.
- A second toolchain, Node and TypeScript, sits beside Go.
- The policy allows inline styles (`style-src 'unsafe-inline'`), but still no inline script and nothing remote.
- The page needs script, so it cannot be read with scripts off.
- The conformance test, the profile's tests and the tests of the page source are the wizards' security argument. The security note of every pull request that changes the page cites the row it touches.
- The catalogue is one more file to keep true when a command changes; a command whose text is missing fails the wizard's test.
- A process that lives between commands is a longer-lived target than one that lives for a command. A program of the same user can open the socket, but it could run the command line anyway, and a card ceremony still needs the PIN and the touch; it can read the process's memory as it could any program of that user, which is why nothing secret stays there between calls.
- A process of an older version may still be running after an upgrade; the command that finds it asks it to stop and starts the new one.
- A test or a script that starts a process must stop it (`ritueel stop`) or leave it to end by itself.
- The loopback port, while the page is in use, stays reachable by other processes of the same user, and a browser extension can read the page. The profile says so, and the design assumes it.

## Roads not taken

- **A click to confirm, protected by the token.** The friendliest flow, but any process that can read the cookie or the page, an extension included, could confirm a plan; only the terminal and the touch are out of its reach.
- **A confirmation code shown in the page and typed in the terminal.** Almost the same, but the thing to compare would come from the page that might be lying; the plan digest is printed by the terminal first.
- **A full-screen terminal interface.** Nicer on a good terminal, but it hides the transcript, defeats screen readers and cannot be tested through a pipe.
- **A hand-written page (the earlier design).** HTML templates, one stylesheet and one script, with no package tree and no inline style, but plain screens, a second stack beside sluis, and no page that doubles as the public demo; the maintainer chose the stack of sluis.
- **A second API only for the page (plain JSON handlers).** Nothing to learn beyond HTTP, but the command line and the page would call two things that can drift apart; the maintainer asked for one API.
- **A service started at login or boot that both faces call.** Always warm, one process for both, but it must be installed on every system, it outlives the person's presence and could act on roots while nobody is there; the maintainer chose a process started on demand.
- **Every command its own process, with no shared API path.** Nothing lives between commands and there is nothing to stop, but the command line would call the engine inside its own process while the page calls another, two paths to one ceremony that can drift apart; the maintainer asked for one API that works the same way for both.
- **The command line over the loopback address as well.** One door to test, but a port every local process can reach would carry the confirmation; the Unix socket is per user.
- **Open the browser for the person.** One step fewer, but the token would travel on a command line that other processes read.
- **A separate engine for the wizard.** Freedom to shape the flow, but two implementations of the ceremony to test, the failure that [0007](/decisions/0007-ritueel-teaches-and-its-tools-simplify-the-ceremonies/) names.
- **The wizard prepares the card and the account.** One guided path from the box, but [0008](/decisions/0008-the-operator-prepares-the-holder-and-ritueel-creates-attests-and-verifies-the-root/) keeps the tool out of PINs and accounts, and a wizard is no exception.
