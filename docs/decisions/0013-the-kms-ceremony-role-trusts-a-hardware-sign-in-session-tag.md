# 0013 — The KMS ceremony role trusts a hardware-sign-in session tag

**Status:** Accepted
**Date:** 2026-11-06

## Context

[0004](/decisions/0004-ceremonies-plan-confirm-reserve-sign-verify-record/#kms-roots-and-wizards) and [0008](/decisions/0008-the-operator-prepares-the-holder-and-ritueel-creates-attests-and-verifies-the-root/#the-cloud-root) make a KMS root signable only through a ceremony role that "needs multi-factor authentication", and [the KMS reference](/reference/kms-root/#the-key-policy) writes that as the condition `aws:MultiFactorAuthPresent`. A card root has a person's PIN and touch; a KMS root has no card, so this role is the only proof that a person is present. The proposal is [issue #101](https://github.com/truvity/ritueel/issues/101).

The condition cannot be met by many operators. AWS documents that `aws:MultiFactorAuthPresent` "is not present for federated identities or requests made using access keys" (IAM global condition keys, read 2026-11-06). An organisation whose people reach AWS only through a federated sign-in, with no IAM users, can never pass it, so the root could not be used at all. The same page suggests the way out: "pass the authentication method from your identity provider to AWS as a session tag".

Three facts of AWS, read 2026-11-06, bound the design:

- **A session tag comes from the sign-in only when a federated provider assumes the role.** The identity provider puts it in the signed OIDC token or SAML assertion, and the role's trust policy must allow `sts:TagSession`. The caller of `AssumeRoleWithWebIdentity` or `AssumeRoleWithSAML` cannot add or change it. The caller of `AssumeRole`, however, passes its own `Tags`, so any principal that may assume the role and call `sts:TagSession` can set any tag ([session tags](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_session-tags.html), read 2026-11-06). A session tag overrides a tag of the same key attached to the role.
- **The tag is visible to policy, not to the caller.** `aws:PrincipalTag/<key>` is in the request context of every call the session makes, so a key policy can test it. No API returns a session's own tags: `sts:GetCallerIdentity` returns the account, the ARN and the user id, and `sts:GetSessionToken` can be called only with an IAM user's or the root user's long-term credentials.
- **Freshness cannot be compared with the clock.** Policy variables cannot be used with date operators, so a tag holding an expiry time cannot be checked against `aws:CurrentTime`; `aws:TokenIssueTime` is compared only with a fixed date; `sts:DurationSeconds` does not apply to the assume-role operations. What bounds a session is the lifetime of the token it was made from, which AWS refuses once expired, and the role's maximum session duration, which is at least one hour.

## Decision

**The ceremony role is gated on a session tag that the identity provider sets after a sign-in with a hardware key, and only a federated provider may assume it.** We replace `aws:MultiFactorAuthPresent` with it, and change nothing else about the ceremony.

- **The tag.** Key `mfa`, value `hardware`. The provider sets it only when the sign-in that produced the token or assertion used a device-bound hardware key (a security key or a card), checked by the provider; a software or synced passkey, a one-time code or a password does not set it. In an OIDC token it is the claim `https://aws.amazon.com/tags`, then `principal_tags`, then `mfa`, whose value is an array of one string (`["hardware"]`); the flattened form is the single claim `https://aws.amazon.com/tags/principal_tags/mfa` with the string `hardware`. In a SAML assertion it is the attribute `https://aws.amazon.com/SAML/Attributes/PrincipalTag:mfa`. A provider may add `auth_time` (seconds since 1970) for the audit trail; no policy tests it.
- **The key policy.** The `Sign` statement of the ceremony role keeps its two `kms:` conditions and gains `StringEquals` on `aws:PrincipalTag/mfa` with the value `hardware`, in place of `aws:MultiFactorAuthPresent`. The tag is a condition of the key's own policy, so it holds for every path to the role, whatever the role's identity policies say.
- **The trust policy** (the operator's; the full text is in [the KMS reference](/reference/kms-root/#the-hardware-key-proof)). Its only `Principal` is the federated provider (`Federated`): no `AWS` principal, no account root, no other role. It allows `AssumeRoleWithWebIdentity` or `AssumeRoleWithSAML` and, in a second statement, `sts:TagSession`, and puts `StringEquals` on `aws:RequestTag/mfa` = `hardware` on both statements, so a call without the tag fails and a tag attached to the role cannot stand in. Its maximum session duration is the minimum, one hour.
- **Role chaining into the ceremony role is forbidden.** `AssumeRole` takes caller-supplied `Tags`, so a principal that can assume the role could write `mfa=hardware` itself and the proof would prove nothing. That is why the trust policy names no `AWS` principal at all.
- **What the provider must do.** The proof is only as good as these obligations, and the operator chooses a provider that meets all of them:
  - it asks for a fresh hardware-key sign-in for each ceremony (`max_age` in OIDC, `ForceAuthn` in SAML) and sets the tag only if `auth_time` meets that recency;
  - the token or assertion lives 5 minutes or less;
  - it never mints a token that carries `mfa=hardware` from a refresh token, a session cookie or an earlier sign-in without a fresh hardware-key sign-in.
- **Freshness is the sum of two bounds, for one hop.** AWS offers no clock check here (see the context), so the proof is bounded by the provider's token (5 minutes or less) plus the role's session (one hour): about an hour and five minutes at the last use. The tag is not transitive and chaining is forbidden, so it cannot be carried to another session. For a tighter bound the person's SDK credential chain (the profile or environment setting that asks for a `DurationSeconds`, not role chaining) requests a 15-minute session, which AWS allows.
- **Which providers can set the tag.** Any provider that can assume the role directly and meets the obligations above: an OIDC provider through the token claim, or a SAML provider through the assertion. A system that holds intermediates, such as sluis, can be one when its AWS role exchange sets the tag from a policy, after a step-up (RFC 9470) to a hardware-attested sign-in; that is its own decision and is not assumed here. The proof is a standard AWS mechanism that any provider can set, so ritueel and the systems it hands intermediates to stay loosely coupled ([0001](/decisions/0001-scope-roots-and-transitions-systems-like-sluis-hold-intermediates/)); ritueel names no provider. IAM Identity Center is not on the list (see the roads not taken).
- **ritueel does not set, mint or read the tag.** It cannot read it: check 9 of [the KMS reference](/reference/kms-root/#the-checks) asks AWS instead, with a `Sign` call under `DryRun`. **Unverified:** it is assumed, from the AWS documentation, that a dry run evaluates the key policy's principal-tag condition as the real call does; the documentation does not say how CloudTrail names the event or its error code. The test on [issue #12](https://github.com/truvity/ritueel/issues/12) settles it before the check is built. If a dry run skips that condition, check 9 drops the pre-check and the ceremony's first real `Sign` fails closed: AWS denies it and nothing is signed. A real `Sign` over a fixed test digest was weighed and refused, because it is a signature by the root. A missing proof is `kms-session`, exit code 4 ([exit codes](/reference/cli/#exit-codes)).
- **Card ceremonies do not change.** PIN and touch, always ([0004](/decisions/0004-ceremonies-plan-confirm-reserve-sign-verify-record/#who-signs-and-when)). The renewal role stays without a person and without the tag ([0008](/decisions/0008-the-operator-prepares-the-holder-and-ritueel-creates-attests-and-verifies-the-root/#renewal-of-a-cloud-root-under-a-policy)).
- **Enforced: later.** This record fixes the design. The key policy, check 9 and the guide are built with the `aws-kms` store, against a test account ([issue #12](https://github.com/truvity/ritueel/issues/12)); until then the documentation is the target state and nothing is checked.

## Consequences

- A federated operator can run a KMS ceremony; with `aws:MultiFactorAuthPresent` they could not.
- The proof is only as good as the provider's statement. AWS cannot see how the person signed in, and a provider that sets `mfa=hardware` without checking it, or mints it from a refresh token, defeats the gate. ritueel teaches this, and the person still types the plan digest at the terminal; the tag is one barrier among those.
- A recent sign-in is a bound of about an hour, not a minute, and holds for one hop. A ceremony that needs a tighter bound asks the provider for a shorter token and the SDK credential chain for a 15-minute session.
- A person cannot reach the ceremony role from an existing AWS session. They sign in to the provider again for each ceremony; that is the point, and it costs a sign-in.
- If the test confirms it, check 9 makes a `Sign` call with `DryRun`. It appears in the audit trail as a `Sign` by the ceremony role, so an alarm on `Sign` may fire for it; the guide tells the operator to expect it.
- A tag name is now part of the operator's setup. A provider that spells it differently fails closed.
- The pages that said "multi-factor authentication" for the KMS role say "a hardware-key sign-in" instead; a card's PIN and touch are unchanged.
- ADR 0004 and 0008 were reworded in place, as the design phase before the first release allows ([decision records](/contributing/decisions/#changing-a-record)); their dates are the day of that rewording, as the decisions README defines the field.

## Roads not taken

- **A dedicated IAM user with a hardware MFA device.** `aws:MultiFactorAuthPresent` would work unchanged, but it adds a long-lived principal with an access key, which is what an account reached only by federation avoids, and a second MFA device to keep.
- **Drop the condition.** The simplest, but a KMS root has no card, so the typed digest and the role's trust alone would let any session that can reach the role sign for the root; too weak for the root of a trust chain.
- **Reach the ceremony role by role chaining, from a person's session or another role.** No second sign-in, but `AssumeRole` takes caller-supplied `Tags`, so anyone who may assume the role could set `mfa=hardware` themselves; the trust policy names the federated provider only, and chaining is forbidden.
- **IAM Identity Center as the provider.** People already sign in there, but three facts of its documentation (read 2026-11-06) stop it: a directory attribute mapping for the same key replaces the value the identity provider sends ([attributes for access control](https://docs.aws.amazon.com/singlesignon/latest/userguide/attributesforaccesscontrol.html)); the roles of a permission set are managed by IAM Identity Center, so the operator cannot give them the trust conditions ([permission sets](https://docs.aws.amazon.com/singlesignon/latest/userguide/permissionsetsconcept.html)); and a separate ceremony role reached from an SSO session is role chaining. IAM's account access manager is documented to allow custom trust policies; whether it removes these problems is untested and not assumed.
- **A tag that holds an expiry, checked against the clock.** An exact freshness, but AWS allows no policy variable in a date comparison, so it cannot be written; the two bounds above are what AWS gives.
- **`aws:MultiFactorAuthPresent` with `BoolIfExists`.** It would pass federated sessions, but only because the key is absent, so it would also pass a federated session with no second factor.
- **ritueel reads the tag and decides.** It would let ritueel print a better message, but no API returns the session's tags, and a check the key policy does not make is not the gate.
- **A real `Sign` over a fixed test digest as the pre-check.** It tests the real path, but it is a signature by the root key, logged as a use of the root.
- **Name one provider in ritueel.** Easier to document, but it couples the products; the tag is standard, so any provider that sets it works.

- Track the enforcement and the wording in the pages that name the role ([issue #101](https://github.com/truvity/ritueel/issues/101)).
