# 0006 — A bundle is for one organisation or one person; a person writes only wanted files, its history is write-once and its trust files are numbered sets

**Status:** Accepted
**Date:** 2026-11-13

## Decision

1. A bundle is a directory of plain files with a fixed structure. It holds all that ritueel knows about one organisation or one person: the wanted files, the root keys' certificates, public keys and attestations, digests of the revocation signatures, the trust files, the sealed card secrets and the wrapped backup of a person's encryption subkey. It never holds a private key in clear, a PIN the holder types, a passphrase, or a revocation signature itself.
2. One bundle is for one organisation or one person, with its own history and hash chain, trust sequence, root list and one root of each kind it uses. The keys of a root are labelled A and B, then the next letter. A holder with a personal key and a company keeps two bundles, with nothing of the person in the company's files.
3. Across bundles a root key is written with the bundle's name (`acme/A`); inside a bundle it is `A`. A bundle is named by its directory; the flag stays `--dir`.
4. The word "bundle" always means the directory. The trust file is always "the CA bundle"; the file of attestation intermediates is "the attestation bundle". On the site, in the pages and in contract names, this directory is called "bundle", never "directory" or "folder".
5. A person writes only wanted files, only on the workstation: `ritueel.yaml` and one strict YAML file for each object. Everything the program writes is JSON or a standard format. A card's files are named by a name the holder gives, not by its serial.
6. Requests and answers sit together in `requests/<name>/`: the request and, once given, its answer.

7. The history is the write-once part of the bundle: the folder `history/`, with one ceremony folder per ceremony. It holds copies of the wanted files used; its other files are on [the ceremony record page](/reference/ceremony-record/#the-ceremony-folder). ritueel needs no git.
8. A ceremony record is a JSON file, written last in its ceremony folder, with the wanted files and the artifacts with their digests ([its members](/reference/ceremony-record/#the-record)); it holds no secret. Ceremony records form a hash chain checked by the history check. A root does not sign them. The digest of the end of the history goes into the next signed root list, which anchors the chain without another use of the root.
9. The transcript is what ritueel printed, written by ritueel, never a capture of the terminal. A saved plan is written by the running process inside the bundle at `history/<ceremony>/plan.json` (with `--plan-only`), not in a pending area and not as a loose file.
10. ritueel stores the OpenPGP creation time of every key it makes or binds: for a KMS key as a key tag and in every published certificate, for an adopted key only in the bundle and the certificate.
11. After every ceremony and every join ritueel prints the end of the history: eight characters and the count of ceremony records. Advice to the holder, not enforced: keep the bundle in a git repository of its own, back it up to a second remote, and keep that print apart from the repository ([the advice](/reference/bundle/#the-end-of-the-history)). The bundle is part of every key's identity, as it holds the OpenPGP creation times. Losing it is a loss, and the backup is practised.

12. The trust files are written as numbered trust sets, one per change ([what a set holds](/reference/bundle/#the-layout)). A personal bundle has no root list or CA bundle, so its set is just the person's public certificate.
13. ritueel builds the trust files outsiders install: CA bundles, signed root lists, SSH CA key lists and the keyring file of release keys, which the release pipeline packages. The user's own pipeline publishes them. [Record 0011](0011-publishing-and-what-to-do-after-a-ceremony.md), rule 1, says what ritueel changes, sends out and prints.
14. The trust sequence is one integer per bundle that grows by one whenever any trust file changes. Every trust file carries it ([where](/reference/bundle/#where-the-trust-sequence-is-carried)). There is no second counter. A hand-off answer names its sequence, and the requester holds a root list at least that recent before it installs.
15. The exact members, encoding and signature format of each trust file are reference pages with test vectors. They follow this design and cannot change it.

16. The root list holds the active root keys, each pinned by a digest of its public key (for OpenPGP, the primary's fingerprint), with the sequence, the signing time, the expiry and the digest of the end of the history ([the members](/reference/root-list/#the-list)). Its members keep the names `roots` and `label`. It pins keys, never certificates. It and the SSH CA key list are signed with an X.509 root key, because their audience, lifetime, revocation and callers are those of the root.
17. A root list entry for a root key that has no OpenPGP primary leaves out `openpgp_fingerprint`. A reader takes such an entry as a key with no OpenPGP primary and does not refuse it.
18. A list with the same root keys is signed by any one active root key, the one used at that ceremony. A list that changes the root keys carries, for every active root key of the list it replaces, that key's signature or its stored removal authorisation, and every key it adds signs it. Adding, retiring and revoking a root key all change them.
19. The removal authorisation is a statement each root key signs over its own pin when it is born, kept with the revocation material. A root key that can no longer sign leaves the set with it.
20. The root list is re-signed at every yearly ceremony and every transition, so at least once a year. It expires 13 months after signing; status warns at 60, 30 and 14 days before. A missed yearly ceremony is visible to every host after 13 months, not only to the holder.
21. A host refuses a list with a lower sequence than the one it holds; a list with the same sequence whose content differs (only the same list again is accepted); a bad signature; a list no active root key of the held list has signed; a change of root keys lacking every current root key's signature or removal authorisation; and an expired list. When the held list expires and no newer one arrived, the host keeps the last good list and raises a warning. It does not drop its roots.
22. Full TUF, with separate roles and thresholds, is not used.
23. The CA bundle is the certificates of the active X.509 root keys in one PEM file ([the file](/reference/root-list/#the-ca-bundle)).

24. An intermediate certificate is revoked by a CRL, one per issuing root key. A root key signs its CRL at every ceremony in which it signs, and when it is born (empty if nothing is revoked); the CRL of every other active root key is copied unchanged beside it. A CRL is valid for 25 months, and an entry lasts until the certificate it names expires ([the profile](/reference/crl/#the-profile)). OpenPGP is not covered by CRLs. No certificate carries a CRL distribution point.

25. Hosts trust a signed, versioned list of SSH CA public keys. The SSH CA keys of a system that holds delegations stay with that system, as an SSH CA key is an anchor, not a chain. The break-glass SSH CA is ritueel's own root of the kind SSH CA, held offline like the other root keys.
26. The SSH CA key list holds those system keys and the break-glass SSH CA keys of the root keys that keep one. It has the same expiry and host rules as the root list, takes ECDSA P-384 keys only, and nobody edits it ([its format](/reference/ssh-ca-key-list/#the-list)).
27. A system's SSH CA key enters by a third hand-off request type, `ssh-ca-key`: the public key and an SSH signature as proof of possession ([the request](/reference/hand-off-contract/#ssh-ca-key)). ritueel checks it, a person confirms it, and the key, a delegated key, is listed under a delegation the holder declared with that type. The answer says the key is listed (nothing to certify).
28. Each SSH CA key has a use, user or host, asked in the request and fixed by the holder's declaration, so a host never trusts a user CA as a host CA or the reverse.
29. A break-glass SSH CA key is made by ritueel in the key store of its root key when that key is born, and leaves the list with it. An SSH CA key is withdrawn by the next list. There is no revocation signature for it, and the list may be empty.
30. A delegation lists permitted DNS names beside permitted URI hosts. ritueel writes the requested ones into the intermediate certificate as a name constraint and refuses a request for a name that does not equal an entry. This comes with M2.

31. A ceremony only adds files, each named by its identity (a digest or a time) and written whole or not at all ([how a file is written](/reference/bundle/)). A listed file that fails its digest is an error, never absent. On the stick, while a ceremony runs, its attempt and journals are trace records in the [trace area](/reference/trace-area/); ritueel makes the files from them when the ceremony ends ([record 0005](0005-a-ceremony-and-where-it-runs.md), rules 36 and 39).
32. A temporary name is at most 15 characters long: a fixed prefix and a random part. It does not carry the final name.
33. When a write or a flush returns an error, ritueel stops at once with an error. It does not retry, and it does not print the line that says the write was flushed. The same holds for a write to the trace area, and the line that says a trace record is confirmed is not printed.
34. A trust set that no ceremony record lists is an unfinished ceremony when an open attempt of that ceremony exists, as a file or as an open ceremony in the trace area, and the next command finishes it. With no such attempt, the check reports it as a sign that the newest ceremony record was removed.

35. Coming back from the stick is a join: ritueel adds the missing files and never merges text. Two ends of the history are a fork, a critical finding. Two answers to one request stop the join.
36. A join writes no ceremony record; it only adds files, so the end of the history changes only when a ceremony happens.

37. Beside `ritueel.yaml`, the folders of a bundle are named `want/`, `seen/`, `sealed/`, `roots/`, `requests/`, `history/`, `trust/` and `drills/`, and the files of a ceremony folder `plan.json`, `attempt.json`, `births.jsonl`, `signatures.jsonl`, `transcript.txt` and `record.json`. Names are lower case and have no spaces.

38. A name of a file or a folder in a bundle holds only the ASCII letters, the digits, the dot, the hyphen and the underscore. Before it touches the file system, ritueel also refuses a name that is empty, is `.` or `..`, is longer than 255 bytes, is a device name of Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9` and `LPT1` to `LPT9`: the part before the first dot, in any case), or ends with a dot; a name that stays and starts with the prefix of a temporary name (rules 32 and 39), in any case; and two names of one set that differ only by case. The table is on [the bundle page](/reference/bundle/#names).

39. A temporary name is `.rt-` and 11 random lower-case letters and digits, 15 characters in all. This is the fixed prefix of rule 32. A new temporary name is drawn for each file and for each set of files, and it is in the same folder as the final name it is for. In a path that ritueel writes, no element starts with `.rt-`, in any case: not the last one and not a folder on the way, so a final name never meets a temporary name and no file is written into a temporary folder that a stop left. A path that is only read may name one.

40. A file is written in five steps. (1) ritueel creates the file under a temporary name (rule 39), in the folder of its final name. The create fails if that name exists. (2) It writes the whole content. (3) It flushes the file: it asks the system to put the data on the disk. (4) It renames the file to its final name with a rename that refuses to replace. If the final name exists, nothing changes and the write fails. (5) It flushes the folder, so that the new name is on the disk. If the system or the file system cannot refuse to replace, the write fails: ritueel has no other rename. A cut before step 4 leaves no file at the final name. A cut after step 4 leaves the whole file there, if the flush of step 3 reached the disk. The mode of a file must give its owner the read bit, and it may hold no bit beyond the permission bits: another mode is refused before anything is written.

41. A set of files, such as a trust set, is written as one folder. (1) ritueel makes the folder beside its final name, under a temporary name, with access for the owner only. (2) It opens the folder and checks that it is empty: if it holds anything, the write stops with an error, because it is not the folder that ritueel made. (3) It writes each file into it under the file's own name, with steps 1 to 3 of rule 40: create, write, flush. (4) It flushes the folder. (5) It renames the folder to its final name with a rename that refuses to replace. (6) It flushes the parent folder. A cut before step 5 leaves a folder with a temporary name and no set at the final name. Two names in one set that differ only by case are refused (rule 38).

42. An empty folder, such as a ceremony folder, is made at its final name in one call, and its parent folder is flushed. It needs no temporary name, because it is whole when it is empty. If anything has that name, the call fails. The mode of a folder must give its owner the read, write and search bits, and it may hold no bit beyond the permission bits: another mode is refused.

43. The attempt is written like every other file (rule 40): its final name is taken once, and a second write of it fails because the name exists. A journal is the one kind of file that stands at its final name while it grows. It is made empty by a create that fails if the name exists, and then the file and its folder are flushed. A line is added by one write of the line and its line break together, and then the file is flushed. A line that holds a line break is refused, and nothing is written. A reader takes the bytes after the last line break as a half line: it counts as not written, and the reader returns it apart. This holds for a bundle that is not on the stick. On the stick, while a ceremony runs, the attempt and the journals are trace records in the [trace area](/reference/trace-area/) ([record 0005](0005-a-ceremony-and-where-it-runs.md), rules 36 to 41), and the files are made from them when the ceremony ends.

44. The first error stops the writer for good. An error of a step of rules 40 to 43 ends the writer: a create, a write, a flush, a rename, the walk to a folder, the check that the folder of a set is empty, or the draw of a temporary name. This includes the error "the name exists". ritueel does not retry. Every later call of the writer and of its journals returns that first error, whatever its arguments are, and reaches nothing on the disk. Only the release of the open files is left. A name or a mode that ritueel refuses before it touches the file system (rules 38, 40 and 42), a line with a line break, and a failed read are not errors of a step, and they do not stop the writer. This is rule 33, said for the writer.

45. The write steps delete nothing. A file or a folder under a temporary name that a stop or a cut left stays where it is. A temporary name is never read as a record or as a part of a bundle: a reader skips every name that starts with `.rt-`, in any case, because a temporary folder holds whole files under ordinary names. A path that is only read may name such a leftover, to look at it.

46. A name that a reader gets from the list of a folder is data from the stick, not a name that ritueel made. The reader checks each such name by rule 38 before it shows the name or uses it in a path. It shows a name only with every character beyond printable ASCII written as an escape.

47. An intermediate's request states what its certificates are for, in the extension extended key usage. It is required in version 1 of the hand-off contract and is not critical. It names serverAuth, clientAuth or both, each once, and a request without it, or with another purpose, is refused with `policy` ([the contract](/reference/hand-off-contract/#the-request)).
48. The key of an intermediate is ECDSA on P-384 in version 1, and a request for another key type, P-256 included, is refused ([the contract](/reference/hand-off-contract/#the-request)).
49. A host also refuses, as `malformed`, a list whose `expires_at` is not exactly 13 calendar months after `signed_at`, and a list whose `signed_at` is later than the host's own clock ([the checks](/reference/root-list/#how-a-host-reads-it)).
50. A list that is byte for byte the list the host holds changes nothing, so the host takes it without the checks of a change: that every signer is known, the removals, and the change of root keys. It still needs a signature by a root key the host trusts, every signature must verify, and the expiry applies.
51. The operator of a host that holds only initial pins may give it, by the channel of the pins, the lowest sequence to accept. The host refuses a list below it as a rollback, as rule 21 does against a held list.
52. A certificate of a CA bundle has the key of a root key of the list, names itself as its issuer, verifies with its own key (a root certificate signs itself) and is a CA certificate, so that its text is what the root key signed (rule 23).
53. A list that removes at least one root key of the held list, and passes the checks of a change of root keys (rule 18), is not refused for a lower sequence (rule 21). It becomes the held list with its own sequence.

## Why

A holder must prove what was done, and outsiders must check the roots. One bundle for each organisation or person keeps a person's files apart from a company's. A write-once history shows a rewritten ceremony. One trust sequence and an expiry on every list let a host tell a current set from a stale one. On exFAT, a file or folder renamed from a long temporary name to a shorter final name kept a folder entry with a wrong checksum until the system wrote the entry again ([the trial](../research/exfat-power-cut-2026-11-12.md)); a name of at most 15 characters fits in one name entry, so the rename never shortens it (rule 32). A power cut between the rename of a trust set and the ceremony record leaves a trust set no record lists, and that is not tampering when the attempt is still open (rule 34). A failing stick is shown by its error and not hidden by a retry, and a line that says "flushed" must never follow a write that failed (rule 33); the lines on a real stick in [record 0005](0005-a-ceremony-and-where-it-runs.md) say what this does not cover. A name of only the characters of rule 38 has one spelling on every system: no letter looks like another, no accented letter has two forms, and no system folds the case of a letter in another way. The write steps of rules 39 to 45 are the order that two runs on a stick image tried. The correct writer had 0 broken bundles in 252 cuts of run 1, and no run-2 writer broke a bundle in 792 cuts. The three writers that left out a flush, wrote the ceremony record first or wrote the attempt late broke 240 bundles in 504 cuts ([the table by writer](../research/exfat-power-cut-2026-11-12.md#the-image-trials-by-writer)). A journal is flushed at every line, because a line that was not flushed can be lost, and a line must never be shown as written before its flush returned (rules 33 and 43). The writer stops at the first error and deletes nothing, so a person sees what a stop left and ritueel never decides alone what to remove (rules 44 and 45). An intermediate states in its own certificate what the certificates under it may be used for, as the public rules ask of public CAs (CA/Browser Forum Baseline Requirements 7.1.2.10.6; Mozilla Root Store Policy 5.3.1; read 2026-11-13, not read again since); those rules do not bind a private PKI, and the statement costs a request one more extension (rule 47). The public rule for a subordinate CA also marks the extension not critical, and that is the rule taken as the model (rule 47). One curve for an intermediate is one code path to test and to carry in the contract, and no consumer that needs a second one is named (rule 48). The two dates of a list are checked by every host, so that a far expiry or a signing time in the future cannot hide a missed yearly ceremony from the hosts, as rule 20 promises (rule 49). After a revoke or a retire, a host that fetches the current list again would otherwise get a refusal at every fetch, and an operator learns to ignore refusals (rule 50). A host with only pins has no sequence to compare, so a floor that the operator gives with the pins keeps an old list from coming back (rule 51). A CA bundle judged by its keys alone would let a client take its limits from text that the root key never signed (rule 52). To remove a root key a host already asks for every other root key's signature, or the removed key's stored authorisation, and one stolen key cannot give that, so a list that clears this bar may also reset the host's number, as The Update Framework lets its root file rotate the keys of its other files (rule 53; [the note](../research/root-list-sequence-and-a-stolen-key-2026-11-14.md)).

## What it costs

- The bundle holds sealed secrets, so it must be guarded and backed up.
- A change of the root set needs more signatures than a renewal.
- The root list must be re-signed once a year.
- A temporary name says nothing about the file it holds, so a person reading a stopped write finds out from the digests that `close` lists (rule 32).
- The check needs the attempt to tell an unfinished ceremony from a removed ceremony record (rule 34).
- A short fault of the stick ends the ceremony, and the person starts the command again (rule 33).
- Every file costs two flushes, one of the file and one of its folder; a set costs one flush for each file and two more; every journal line costs one flush (rules 40, 41 and 43).
- A stop leaves temporary files and folders that stay until a person or a later command deals with them, and a name that exists is a stop too, so a caller that wants to know whether a name exists reads first (rules 44 and 45).
- A system that needs both server and client certificates states both purposes (serverAuth and clientAuth) in its request, or uses two intermediates (rule 47).
- A requester must put extended key usage in every request; the contract changes in version 1 before any release, and the requesters, sluis among them, follow (rule 47).
- A consumer that takes only P-256 is not served by an intermediate (rule 48).
- A name cannot hold a space or a letter of another script, so the name of a person or an organisation lives inside the files, and the name of a file is plain ASCII (rule 38).
- A host whose clock is behind refuses a fresh list and keeps its old one, which is the safe side (rule 49).
- A host that holds only initial pins takes a first list on one signature for everything it says beside the pins, and takes an old list that is validly signed and not expired, also one that holds a root key that was revoked since. A lowest sequence closes the second case, and it is one more number for the operator to look after (rule 51).
- A removal authorisation is a permission for whoever holds it: one stolen root key, the stored authorisation of another root key and a new key can replace the whole set of root keys. The protection against a takeover with one key is as strong as the secrecy of the stored authorisations (rule 19).
- A CA bundle must be built with certificates that sign themselves, which is one more rule for the page and the test bundles (rule 52).
- A list that keeps the same root keys can still be frozen by a thief's higher sequence, until the stolen key is removed; the host judges a list that removes a key by the checks of a change before its sequence, so the order of the checks changes for it (rule 53).

## Roads not taken

- **Several organisations or people in one bundle.** One set of card files, but it needs a layer between bundle and root, renames the keys A and B, and mixes a person's files with a company's.
- **The bundle name is the root name.** Shorter, but a host pins A and B one by one, so `acme/A` names the root exactly.
- **Keep the word "directory".** No rename, but key, revocation and working directories are directories too.
- **Another word (dossier, vault, book, home, realm).** No clash with the CA bundle, but "bundle" is the word and its clash with the CA bundle is accepted.
- **A hosted history.** Nothing to back up, but a service every ceremony trusts, and ritueel has none.
- **Sign each record with the root.** A third party could check a record, but it is a third use of the root and one more touch.
- **Capture the terminal as the transcript.** Complete and free, but it can hold what was typed.
- **The word "products" and a folder of that name.** The word is unclear.
- **Requests and answers in separate places.** Answered and waiting requests are seen in one place.
- **A counter per trust file.** Each moves alone, but a requester would need three numbers to tell whether it is current.
- **Pin root certificates.** Easier to compare, but the yearly re-issue would break every pin.
- **A separate key for the list and the SSH CA keys.** Separates their signer, but costs a slot and a touch for a key with the same audience, lifetime and revocation.
- **Any one active root changes the root set, as it renews the list.** One signature for every list, but the trusted set would rest on one root.
- **Every current root signs a change of the set, with no stored authorisation.** Simplest strict rule, but a lost root could never leave the set by a signature and every host would need its pins replaced by hand.
- **A separate key for changes of the root set.** Keeps renewals and changes apart, but one more slot and touch per root for a key with the same audience.
- **A root list with no expiry.** Nothing to renew, but a list that stopped being signed cannot be told from a current one.
- **Accept any list at an equal sequence.** Simpler, but two different root sets could carry one sequence.
- **Fail closed when the list expires.** Stronger on paper, but a missed ceremony would cut every host off its roots at once.
- **Full TUF.** Mature freeze and rollback protection, but standard verifiers cannot count signatures and one holder cannot staff separate roles.
- **The holder edits the SSH CA key list.** No request to write, but a key would be trusted that nothing checked and the list would have a second author.
- **Extended key usage optional in a request.** A request would need nothing more, but an intermediate would not state what the certificates under it are for, which the public rules ask of public CAs (rule 47).
- **Extended key usage critical in a request.** One rule for all four extensions of the request, but it departs from the public rule for a subordinate CA, and no source read says that the flag adds protection here (rule 47).
- **Refuse the same list again after a change.** Nothing to build, but every fetch of the current list is a refusal after a revoke or a retire (rule 50).
- **Check only the 13 months of a list, or leave both dates to the writer.** A smaller rule or none, but a signing time in the future walks around the first, and rule 20 then holds only if the writer keeps the rule (rule 49).
- **Judge a CA bundle by its keys only and say so on the page.** No new rule, but a certificate with the right key and another text passes the check (rule 52).
- **Only the operator's way back for a stolen key.** Nothing to build, but a manual step on every host, which trusts the stolen key until then; record 0007 declined the same road for a lost root key (rule 53).
- **A host takes only the next sequence.** A thief who adds one file goes one step only, but every list must be reachable by its number, a host must walk through them, and it does not recover from a freeze (rule 53).
- **A host takes a list at most a fixed distance ahead.** No walk, but the thief signs the held number plus the distance and the freeze lasts for that many lists (rule 53).
- **A jump of more than one needs every current root key.** It reuses the rule for a change of keys, but a stored authorisation would give a thief the number, and a host far behind needs a ceremony with every card (rule 53).
- **Each list names the digest of the list before it.** A fork is found, but the thief can name the digest of a public list, and the honest list is refused (rule 53).
- **The signed time as the order, as apt does.** No number to run away, but a thief signs at the host's clock and an honest list signed earlier is refused (rule 53).
- **No lowest sequence beside initial pins.** Nothing added to the command, but a first list on one signature and an old list that still holds a revoked root key both stay possible (rule 51).
- **P-256 for an intermediate, as a choice of each delegation.** It would serve a consumer that takes only P-256, but it is a second curve to test and to carry in the contract, and a leaf under a P-256 intermediate must then be P-256 (ETSI TS 119 312, 9.5). A named consumer that takes only P-256 is the event that reopens it (rule 48).
- **Version 2 of the hand-off contract, or a contract of its own, for the SSH CA key type.** Keeps version 1 as written, but nothing is released so no receiver is surprised, and a second version costs every reader a second code path.
- **Ed25519 as a second SSH CA key type.** It is the OpenSSH default, but BSI lists only ECDSA for SSH signatures, a host in FIPS mode refuses Ed25519, and a second type is a second code path ([the sources](/reference/ssh-ca-key-list/#choices-made)).
- **A key that does both user and host certificates.** One key fewer, but its holder can vouch for hosts as well as users.
- **Dropping the break-glass SSH CA.** One kind of root less, but the SSH CA is one of the three kinds of root ([record 0001](0001-what-ritueel-is.md), rule 8) and rule 29 makes a break-glass SSH CA key part of a root.
- **OCSP for an intermediate.** Live status, but it needs a responder that signs online, which ritueel never holds, and a certificate that names it.
- **A CRL distribution point in the intermediate's certificate.** Clients could fetch alone, but the certificate would name a host that outlives it and TLS libraries do not fetch it by default.
- **One CRL for both roots, signed by the root of the year.** One file, but standard clients take a CRL from the issuer only and indirect CRLs are poorly supported.
- **Both roots sign their CRL at every ceremony.** A 13-month CRL like the root list, but it needs both cards every year, which the alternation exists to avoid.
- **Revoked intermediates in the root list.** One signed file, but the list pins keys and would grow with every renewal.
- **One wanted file for everything.** The fewest files, but every edit touches the one file, so any edit makes every saved plan stale, and a proposed change would have to change the middle of a text; one file for each object was chosen.
- **One folder for each object.** A file listing would be the inventory, but certificates and sealed secrets would exist twice and deleting a folder would delete its history; one file for each object and the history folders were chosen.
- **The history in one append-only file, such as a tar archive or a log.** One thing to carry, but an append that was cut off must be repaired by editing a write-once file, and plans and certificates would stay files anyway; one ceremony folder for each ceremony stays (rule 7).
- **A Merkle tree over the history.** A short proof for one entry, but it helps only when someone outside remembers an earlier tree, and ritueel has no such party (a hosted history is a road above); every checker holds the whole history. It can be built later from the stored ceremony records.
- **A storage engine (an LSM store, a B-tree file or SQLite) as the source of truth.** Made for speed and size, but a company bundle gets a few ceremony records a year, and an engine breaks "a directory of plain files" (rule 1) and a join that only adds files.
- **Git as the way back from the stick.** Nothing to build, but "ritueel needs no git" (rule 7) and a holder without git would have no way back; the join (rule 35) does it.
- **URI hosts only for the name constraint of an intermediate.** It needs nothing new, but an intermediate that issues for DNS names would carry no limit on those names, so the policy and a delegation list DNS names too (rule 30).
- **A store of every old text of a wanted file.** Undo without git, but about eight more commands; the exact copies in each ceremony folder (rule 7) and git (rule 11) cover the need until it is built.
- **Merge the text of two copies at the join.** One result, but a merge of a signed answer or of a history would decide which one is true; the join adds files only and shows a fork (rule 35).
- **A name that does not carry its identity.** Short names such as a plain counter, but two copies could hold two contents under one name and the join would no longer be a union; every name carries its identity (rule 31).
- **A ceremony record for each join.** The history would show every join, but two copies that each join would get two ends of the history, which is a fork (rule 35), and a saved plan that names the end of the history would go stale after every join; a join only adds files (rule 36).
- **A note outside the chain for each join.** The holder could see when a copy was joined, but `seen/` is replaced and is not history, so the note would be no record, and it would be a new kind of file to specify (rule 36).
- **An empty value for a missing OpenPGP fingerprint.** Every entry would have the same shape, but an empty value that means "none" looks the same as a value someone forgot to fill.
- **A second version of the root list for bundles without OpenPGP.** An old reader would refuse the file clearly, but two formats would have to be kept for years, for a case that will be common.
- **One more flush of the renamed file after each rename.** It also left no wrong entry in the trial, but it costs one more flush for every file and leaves a short gap between the rename and that flush (rule 32).
- **Both the short name and the extra flush.** It would give two independent protections, but it is slower, and there is more to explain and test (rule 32).
- **A trust set with no record is always an alarm.** The simplest rule, but a power cut at the wrong moment would look like tampering (rule 34).
- **Retry after a write error.** It would work through a short fault of the stick, but it hides a failing stick and may write a mixed state (rule 33).

## Not yet proven or only proposed

- **Not yet proven.** That no older list passes rule 53 except an honest list that removes a key. It is an argument from the rules of the root list, not a test. A replay of every list of a long history against every held list, with initial pins too, and the case of the pin of a removed key that is added again, are still to be run ([#228](https://github.com/truvity/ritueel/issues/228); [what other systems do](../research/root-list-sequence-and-a-stolen-key-2026-11-14.md)).
- **Proposed.** The other names are fixed with the code and the card proofs: the folders inside `want/` (`cards/`, `roots/` and `delegations/`), the file `want/openpgp.yaml`, the folder `wanted/` of a ceremony folder, the files under `roots/<label>/`, the names of the files in `seen/` and `sealed/`, the form of the name of a trust set, and the member names inside the files ([#8](https://github.com/truvity/ritueel/issues/8)).
- **Proposed.** No file stores the bundle's name; `name` in `ritueel.yaml` is the name in the root keys' subjects, and whether it must differ between bundles is open ([#8](https://github.com/truvity/ritueel/issues/8)).
- **Proposed.** Each bundle's card files list the cards for its own rows; the list of rows may be empty, and a card used only for the passkey is listed with applications `[fido2]` ([#8](https://github.com/truvity/ritueel/issues/8)).
- **Proposed.** The rules a request is checked against are split: key store, firmware, PIN and validity in policy; name constraints and KMS read roles in each declared delegation's wanted file. Excluded DNS subtrees and excluded IP ranges, except the one the hand-off contract accepts (every IP address), are not decided ([#70](https://github.com/truvity/ritueel/issues/70)).
- **Proposed.** The repair of a fork: one ceremony record that names every end, a root list signed only when the history has one end, and a result from the stick that counts only after a join has checked it ([#138](https://github.com/truvity/ritueel/issues/138)).
- **Proposed.** What a host does when it is several root lists behind is not said ([#139](https://github.com/truvity/ritueel/issues/139)).
- **Proposed.** What `acme/A` names when one letter labels the keys of several roots in a bundle ([#137](https://github.com/truvity/ritueel/issues/137)).
- **Not yet proven.** That the temporary names of rule 32 leave no wrong folder entry on a real stick; what other operating systems do with such an entry was not tested ([the trial](../research/exfat-power-cut-2026-11-12.md), [#181](https://github.com/truvity/ritueel/issues/181)).
- **Not yet proven.** That the rename that refuses to replace works on a real exFAT stick and on macOS: it worked only in a virtual machine with the kernel of the offline system, the manual page of `renameat2` does not list exFAT, and the code was only cross-built for macOS. Where it is not supported, the writer stops with an error and replaces nothing (rule 40; [#181](https://github.com/truvity/ritueel/issues/181)).
- **Not yet proven.** That the order of the write steps keeps a bundle whole on a real stick: one sector can keep the content of the write before it, and no order of flushes prevents that. The trace area is the answer for the attempt and the journals; the files made from it, and the files of a bundle outside it, are not covered ([the measurement](../research/usb-stick-cut-during-a-write-2026-11-13.md), [#181](https://github.com/truvity/ritueel/issues/181)).
- **Proposed.** What ritueel does to repair a file at its final name that fails its digest, and how a torn file is written again, is not decided: a new write may take the name of a file that was never renamed, but a file at its final name is never replaced. That `check history` reports such a listed file is decided, and is written on [the ceremony record page](/reference/ceremony-record/#the-hash-chain) ([#181](https://github.com/truvity/ritueel/issues/181)).
- **Proposed.** Whether break-glass SSH can work without a root-card ceremony is open: rules 25 to 29 do not say how break-glass is used, no time-to-login target is stated, and the drill for it does not exist yet ([#91](https://github.com/truvity/ritueel/issues/91)).
