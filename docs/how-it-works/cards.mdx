ritueel is in its design phase: the program does not exist, and the pictures show how its cards are designed to be used ([how a YubiKey holds keys](/learn/how-a-yubikey-holds-keys/)). A fourth kind, the rehearsal card, is for practice and tests: it never holds a real key and may be reset.

## Root card

A root card holds roots, and a few jobs of its own: row 1, and the passkey that opens a key file ([record 0003](../decisions/0003-root-cards.md), [record 0002](../decisions/0002-where-a-key-lives.md)). You keep two root cards, A and B. Each makes its own keys; they are never copies, so if one is lost the other still holds a root. The partner root of the same bundle sits in the same row of the second card; the bundle names here are made up.

A root card may be used on your own workstation, under four conditions: a touch for every signature, the number of signatures stated in the plan, no retry of a failed touch, and the result checked against the plan on a second device. It may also be used in the offline system, which stays available ([record 0005](../decisions/0005-a-ceremony-and-where-it-runs.md)).

<Figure name="root-card">
  Six rows of four PIV slots. Row 1 is the card’s own jobs; each other row holds one root of one bundle, the same key kind in each column. Each bundle on the pair keeps its own card list and its own sealed copy of the card’s secrets.
</Figure>

One pair of cards serves up to four bundles. Each card has one PIN, one PUK and one management key, for all the bundles on it. Each bundle has its own card list and its own sealed copy of the card’s secrets. A second bundle gets its copy by a request to the first bundle, which wraps the secrets for it. A row that belongs to another bundle is declared in the card’s file in the bundle ([record 0003](../decisions/0003-root-cards.md)).

<Figure name="two-bundles-one-pair">
  Two bundles on one pair of root cards. Each keeps its own card list and its own sealed copy of the card’s secrets.
</Figure>

A key file opens with a passkey on each root card: the passkey unlocks the key, and a recovery key is kept apart in case the cards are lost. Each bundle has its own unlock key and its own recovery key. This is decided and not yet proven on hardware; if the proof fails, the spare key in 9d is the way ([record 0002](../decisions/0002-where-a-key-lives.md)).

## Day-to-day card

A day-to-day card carries a person’s own subkeys and passkeys. Signing and authentication keys are born on each card; the decryption key is made in software, so a lost card does not lose the mail it decrypted ([record 0008](../decisions/0008-a-persons-own-key.md)).

<Figure name="day-to-day-card">
  One day-to-day card holds one set of OpenPGP subkeys and your passkeys, and nothing in PIV. A second card gets its own set.
</Figure>

## Server card

A server card stays plugged into a server of a requester system, such as [sluis](https://github.com/truvity/sluis), and signs for its services. ritueel lists it and only ever reads it ([record 0003](../decisions/0003-root-cards.md)).
