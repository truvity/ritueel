ritueel guides each use of a root key (the top key of your certificates, or your OpenPGP primary key) and keeps a record of it. A root is what others trust without further proof; it is built from one or more keys. A ceremony is the planned, recorded occasion on which a root is used. Below: three layers of a key, then the ceremony and two real jobs drawn as comics. Jump to [sign an intermediate](#sign-an-intermediate) or [bind the subkeys](#bind-the-subkeys-of-your-card).

A plan is the sheet that fixes what will be signed, except new keys; its digest is a short fingerprint of it. The offline system is a computer started from a USB stick, with no network. A key file is an encrypted file that holds a software key.

ritueel is in its design phase: only `version` is built. These pictures show how it is designed to work.

## Sign an intermediate

A requester is a system that asks for a certificate, such as sluis (a system that issues certificates every day and holds intermediate keys). It needs a certificate for its intermediate key. A root that cannot be copied, on cards or in a cloud key service, may sign on your workstation ([record 0005](../decisions/0005-a-ceremony-and-where-it-runs.md)). The conditions:

- A touch for every signature. This is for a root on cards. A cloud key has no touch: for a cloud root the typed digest and the role session stand, and its audit trail records every signature.
- The number of signatures stated in the plan.
- No retry of a failed touch.
- A check against the plan on a second device.

The last three hold for both kinds. A key in a file is used only in the offline system, which is an option for a root on cards; a cloud root always runs on the workstation ([the stick](/how-it-works/bundle-and-stick/)).

## Bind the subkeys of your card

ritueel binds the subkeys of your day-to-day card to your own OpenPGP primary, kept in a key file. A key file can be copied, so this ceremony runs in the offline system. The signing and the authentication subkey are made in one ceremony.

</Figure>
