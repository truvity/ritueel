# The API of the local page

Status: a design, version `v1alpha1`. The program that serves it is not built, and the page's demo answers the same calls from fixtures (`ui/src/fixtures/`) through an in-memory transport. The contract may change in any pre-release, and no breaking-change check runs. The first build of the page has five reads and no write.

The API between ritueel's local page (`ui/`) and the ritueel process, written in Protobuf (package `ritueel.local.v1alpha1`). The program will serve it with ConnectRPC; the page calls it with `@connectrpc/connect`. See [the demo](https://ritueel.id/demo/) and [the design of the process and the page](https://ritueel.id/design/#the-process-and-the-page).

The process is one ritueel process, the same program as the command line. The first command that needs it starts it in the background, and it is not a service: it is never installed, never started at login or boot, and never outlives logout or reboot. A bundle is the directory with a fixed structure that holds everything ritueel knows about one trust domain; in this contract no call names a bundle, and which bundle the process serves is not decided by the records (record 0010, rules 8 and 9). The process serves the command line and the page on one fixed loopback port (localhost, 127.0.0.1 only; the number is 7488, record 0010). There are two kinds of token. A full-rights token, read from a file only the user can read, is for the command line. A page-rights token is for the browser, is used once, becomes an `HttpOnly`, `SameSite=Strict` cookie and can call only the reads (the five calls below): no call that confirms, signs, creates a key or runs a ceremony is open to it, and the digest is typed in the terminal. Every request is checked for its `Host` and, separately, its `Origin`. Before the command line sends a confirmation or a PIN, the listener proves that it knows the secret in the token file. There is one exclusive lock per bundle. The process keeps no ceremony state and no PIN, and it ends after 15 minutes without a call (never in the middle of a running ceremony), at once on a stop command, and at logout or reboot. Other programs of the same user can reach the port while the process runs, so the page is trusted no more than any other web request. The rules are in [record 0010](../docs/decisions/0010-the-engine-the-process-and-the-page.md), rules 6 to 12.

**No call takes or returns a secret, a PIN or a passphrase.** There is no field for one, and none will be added. **No call writes.** The page is a view: it never confirms a ceremony, and it has no text field. Applying happens in the terminal, in the offline system or on your workstation, where you type the first eight characters of the plan's digest. No value goes from the page to the process except one level to filter findings by, a choice from a fixed list.

## Generate and check

`just proto-lint` lints (buf, from devbox). `just proto-gen` lints and regenerates `ui/src/gen/` with `protoc-gen-es` from the page's lock file (`ui/node_modules`). `just proto-check` regenerates and fails on any difference, so the committed code is always what the generator makes (the version number in the `@generated by protoc-gen-es` line is the one difference it ignores). It also fails on any hand edit of `ui/src/gen/`. Both run in CI.

The Go side comes with the program: `protoc-gen-go` and `protoc-gen-connect-go` as two more entries in `buf.gen.yaml`, and `option go_package` in the two files. The generated handlers are mounted on the one listener; the page-rights token reaches only the reads.

## The service

Every call is a read, marked `NO_SIDE_EFFECTS` so that each may be a `GET`. Every response carries `read_at`, the time of the read. Only `ListFindingsRequest` has a field, `min_severity`.

## Things a designer must know

1. **Text is data.** Every string in a response is written by the bundle, not
   by the program: user IDs, card names, summaries. Render it as text only, cap
   its length, and show any non-ASCII, bidirectional, zero-width or control
   character as a `U+XXXX` escape. The fixture is plain ASCII; real data will not be.
2. **A key is its full fingerprint.** `Key.fingerprint` is complete (40 hexadecimal
   characters for OpenPGP, 64 for an X.509 or SSH key), and so is every `ObjectRef.id` that
   names a key. Never identify a key by a name or a short id. Names (`label`, `name`) can repeat.
3. **Unset means something.** An unset `expires_at` on a key never means *no expiry*.
   For an SSH CA key it means no certificate: the key ends when the next list leaves it
   out (record 0006, rule 25). For any other key it means that no end date is known. An empty `apply_command` means no change is
   ready. An empty `verify_command` means the page has no command for that file (a
   personal bundle has no root list to check it against). An empty `close_command` and an
   empty `publish_command` mean the state of the ceremony offers no such step.
4. **A change not applied yet is one `Change`** (record 0005, rule 29). It has an object
   and the objects it involves, a kind, a state (`ready` or `waits`), the sentence of the
   program, what it needs (a card, a request, a key file), the source it comes from (a
   wanted file, the history, a date or a request) and, when a plan has taken it, the
   ceremony. The page marks a change on its object in every view that lists the object.
5. **The row layout of a card is fixed.** `PivApplication.rows` always has six rows of
   four slots in the order 9a, 9c, 9d, 9e, then 82 to 95. Row 1 is the card's own
   jobs, and `PivRow.key_label` names the key that a row holds. A slot's
   `SlotState` is empty, used, reserved (planned, not born) or spare (a row no root
   owns yet); on a day-to-day card all PIV slots are empty, not spare. A row that
   belongs to another bundle of the same holder (a shared pair of root cards) is
   declared in the card's file and arrives as used slots with `SLOT_USE_OTHER_BUNDLE`
   and no `public_key_sha256`. The value is proposed (record 0003, issue 11).
6. **Counting days.** Use `read_at` as "now", never the browser clock. The page shows
   the time of the read on every screen. It reads when a screen opens and when its window
   gets the focus, and on no timer.
7. **The command is shown, never run.** `apply_command`, `fix_command`, `revoke_command`,
   `close_command`, `publish_command` and `verify_command` are exact strings to display
   and copy. They follow `docs/reference/cli.md`: `ritueel`, one of its thirteen words
   and flags it lists (some are proposals that it marks). No command holds a digest, and
   `apply` never carries `--confirm`: you type the first eight characters of the
   plan's digest in the terminal. `REASON` and `TEXT` in a command are placeholders that
   the page tells the reader to replace.
8. **A root is one for each kind, built from keys.** A company has three roots, an
   X.509 anchor, an OpenPGP identity and an SSH CA, and each is built from keys that sit
   in any place: a card, a cloud key service, a key file. "A" and "B" are keys of a root,
   not roots. In a bundle with a card pair and a cloud key, the label C names three keys,
   one in each root (record 0004, rule 2). A key is written `bundle/label` across
   bundles, for example `acme/A`, and "key A" inside the page. A delegated key (an
   intermediate, a subkey, an SSH CA key) has `role = DELEGATED_KEY` and the name of its
   delegation.
9. **A ceremony has four states.** A ceremony folder is planned (it holds a plan and
   nothing else), started (an attempt without a record), recorded (it holds its ceremony
   record) or closed (a closing record names it). The names are proposed
   (`ceremony-record.md` decides the facts, not the names). A closing record is a
   ceremony of its own, with the command `close` and the state recorded. A plan that was
   never run and is now stale (`Ceremony.stale`) is folded by the page into one line with
   a count. `Ceremony.applied` lists the changes the ceremony made and `left_out` the
   ones it did not, with the reason.
10. **`int64` is a string in JSON** (`size_bytes`), and `Timestamp` is an
    RFC 3339 string; the generated types turn them into `bigint` and `Timestamp`.
11. **The four card kinds** are root, day-to-day, server and rehearsal, and a card
    never changes its kind. A server card (`CARD_KIND_SERVER`) stays plugged into a
    server of a requester system and signs for its services. It is an ordinary card,
    not a hardware security module product; ritueel lists it and only ever reads it, so
    it has no adoption, no sealed file and no layout check. A rehearsal card never holds
    a real key, may be reset, and serves only a test root. A root card holds roots by
    row and may serve up to four bundles of one holder.
12. **A read can be in four states.** Loaded, empty (the read worked and nothing is
    there), failed (the read did not work; the page never draws it as empty) and waiting
    (no answer yet). The process answers loaded or fails; the other states are the
    page's. A page left open for longer than the process lives shows a failed read.
13. **Proposed words are marked.** A word, a state or a kind that no record and no
    reference page decides is marked `[proposed]` in the comments of the two files, and
    the pull request that added it lists them for the maintainer. They are the kinds and
    the two states of a change, what a change needs, the four names of a ceremony, the
    status of the history (the chain states, the time of the last check, the sentence),
    the texts the program writes for a ceremony and a card, the level filter of the
    findings (`ListFindingsRequest.min_severity` and its three labels on To do), and the
    names of the five calls themselves.

## What went with the wizard

The older design had a second service and a wizard in the page. They went with record 0010
and are not built: `PlanService` and its three calls `ListIntentions`, `StartPlan` and
`SavePlan` (the only call that wrote), and the types `Intention`, `DueItem` and the
others of that service, the questions, the plan with its steps and the hand-over. The
page-rights token no longer reaches a write, and the command `ritueel run PLAN --confirm
DIGEST` is not shown. The old `ListRoots` and `ListCards` are one call, `GetInventory`.
